# v0.6.8 release audit

Date: 2026-09-30. The seven findings now have code corrections and regression tests. Publication remains pending.

The initial candidate was commit `ac6aa78`, plus the carrier-default and documentation changes.
The comparison baseline is `v0.6.7`. The initial investigation changed no runtime code or deployed configuration.
The correction phase below records subsequent code and deployment changes.

## Result

The audit found five reliability defects and two additional security defects.
Two reliability defects originate in the new browser recovery code.
The remaining defects exist in the previous release or its deployment templates.
The initial test suite did not detect these defects.

| ID | Priority | Area | Origin |
| --- | --- | --- | --- |
| R1 | P1 | WebSocket input can exceed its memory limit during uplink backpressure | Preexisting |
| R2 | P2 | Stale data for a closed stream can reach a replacement session | New |
| R3 | P2 | One excess stream can terminate healthy streams | New for three carriers |
| R4 | P2 | Atomic configuration replacement loses automatic reload | Preexisting |
| R5 | P2 | A repeated reload conceals a required restart | Preexisting |
| S1 | P1 | Nginx fallback can turn decoded path bytes into upstream headers | Preexisting |
| S2 | P2 | Alternate credential spellings reach the ordinary-site fallback | Preexisting, incompletely addressed by new checks |

Priority reflects the demonstrated mechanism and its potential impact. The audit did not establish that these defects caused the observed trial disconnects.

## Reliability findings

### R1: Unread WebSocket input bypasses its limit

Location: `pkg/webproxy/websocket_transport.go:798` and `:303`.

An outstanding uplink can prevent decoding of the next control frame.
The traffic callback then returns before it calls `boundUnreadInput`.
Subsequent callbacks retain additional bytes without that check.
The gnet event loop copies unread input into a ring buffer after each callback.
This storage is outside the WEB session queue accounting.

The local reproduction retained 2,097,158 bytes against a 65,536-byte control-input limit.
It discarded no bytes and returned `gnet.None` on all 32 callbacks.
Retryable uplink backpressure can keep this state active for up to 30 seconds.
An authenticated connection in this state can consume memory beyond the intended limits.

The reproduction uses a connection double. Source inspection confirms that the real gnet event loop retains unread input.
No exhaustion test ran against a deployed service.

Required correction: enforce the unread-input limit before every early return that retains input.
The regression must cover a pending uplink followed by control input and additional traffic.

### R2: Already-closed streams escape recovery isolation

Location: `pkg/webproxy/bridge_recovery.js:49` and `:75`.

Remote CLOSE removes the stream from `activeStreams` without recording its ID in `closedLanes`.
Recovery records only the IDs that remain active.
An in-flight native DATA message for the closed stream can therefore enter the replacement session.

Normal event ordering can produce this sequence.
The native client posts DATA before it receives CLOSE.
The bridge processes the remote CLOSE and a carrier failure before it processes that MessagePort event.
The replacement server rejects DATA for an ID that it never opened and closes the session.

Scratch tests reproduce transmission of old DATA in both `https` and `websocket`.
Those tests use rendered production scripts with mocked HTTP, sockets, timers, and MessagePort.
The replacement-session rejection follows `session.go:488`, `:892`, and `:1471`.
The reproduction does not exercise a real Telegram client's task scheduler.

Required correction: retain closed-stream IDs across recovery and discard late frames for those IDs.
The regression must include streams that closed before recovery began.

### R3: Excess OPEN terminates the whole bridge

Location: `pkg/webproxy/bridge_recovery.js:37` and `pkg/webproxy/bridge.go:729`.

At the default limit, the 129th simultaneous OPEN throws an exception in `acceptNative`.
The caller converts that exception into terminal bridge failure.
All established streams close with it.

The server previously rejected only the excess stream and retained existing streams.
`TestSessionStreamDialAndPendingLimits/per-session_streams` still verifies that server behavior.
Scratch browser tests reproduce the new bridge-wide failure in `https` and `websocket`.
The same shared code affects `https-lanes`.
The `websocket-lanes` carrier already had a terminal lane-capacity check before this release.

Required correction: reject the excess stream with CLOSE while preserving healthy streams.
Add a browser regression for stream-limit isolation.

### R4: Atomic file replacement loses configuration reload

Location: `pkg/gproxy/hotreload.go:97` and `:114`.

The watcher attaches to the configuration file's inode.
It ignores rename and removal events and does not attach to a replacement inode.
An editor that saves through atomic rename therefore disables subsequent automatic reloads for that file.

The reproduction first confirmed one reload from an ordinary write.
An atomic replacement did not cause another reload.
A subsequent write to the replacement file also did not cause a reload.
The loader count remained one throughout both later operations.

Required correction: watch the parent directory and filter the configured filename, or restore the file watch after replacement.
The regression must cover replacement and a later write.

### R5: Repeated reload clears an unresolved restart warning

Location: `pkg/gproxy/hotreload.go:152` and `:170`.

The reloader stores the last loaded configuration before it compares restart-only fields.
It applies hot fields but leaves restart-only values unchanged in the running service.
Another reload then compares the new file against itself.
It reports success even though WEB configuration or secret changes still require a restart.

The reproduction observed a restart warning after the first WEB fingerprint change.
The second reload reported success while the handler retained its original fingerprint.
This can conceal an incomplete configuration change or credential rotation.

Required correction: compare restart-only fields against the effective running configuration until restart.
The regression must retain the warning across repeated reloads.

## Additional security findings

### S1: Decoded fallback URI permits upstream header injection

Locations: `examples/web-proxy/nginx/nginx.conf:122` and `examples/gateway/templates/nginx-web-server.conf:43`.

The sanitized fallback uses `proxy_pass http://public_site$uri`.
Nginx decodes the path into `$uri` before it constructs this variable-based upstream request.
The isolated reproduction showed an encoded question mark becoming a query delimiter.
It also showed encoded request-line characters producing an additional harmless `X-Probe` header at the public-site upstream.
Thus removing the original request headers does not fully preserve the intended upstream request boundary.

The reproduction copied the exact fallback block into a disposable Nginx container.
The container had no external network, published ports, or production credentials.
A stub upstream returned 419 to select the fallback.
The real Telego classifier can select sanitized fallback from reserved WebSocket-protocol headers before it authenticates a bearer.
This reachability follows `http_server.go:1009` and its `prepare` branches.
The audit did not run a complete Telego-plus-Nginx attack or claim a demonstrated application compromise.

Read-only inspection found the decoded-URI fallback pattern in both NAS and VPS Nginx configurations.
Both configurations passed `nginx -T`.
Syntax validation does not detect this behavior.

Required correction: construct the sanitized upstream URI without inserting decoded control or delimiter characters.
An integration regression must observe the actual request received by the public-site upstream.

### S2: Credential classification misses alternate spellings

Location: `pkg/webproxy/http_server.go:966`, `:978`, and `:1044`.

The credential detectors require literal query names, canonical query values, and the exact `Bearer ` scheme spelling.
A URL-encoded bridge key or value can therefore reach ordinary-site fallback with a reusable capability.
A lowercase bearer scheme can also pass a live token to that fallback.
The fallback preserves the original query and Authorization header for the website.

Local HTTP reproductions returned status 418 and `ordinary-site-v1` for both root and custom-path configurations.
Query decoding recovered the original valid capability.
The new path checks do not fully prevent this preexisting behavior.

Retired canonical bearers also reach ordinary fallback while the manager still retains their closed-token records.
Those tokens no longer authenticate, so that observation has lower impact than disclosure of a reusable capability or live bearer.

Required correction: recognize credential-bearing variants for sanitization without accepting those variants as valid carrier requests.
The regressions must cover encoded queries, scheme case, wrong paths, and retired tokens.

## Coverage and limits

The audit covered the release diff and its surrounding WEB parser, authentication, session, transport, and resource-management code.
It also covered browser recovery, gateway defaults, Nginx fallback, configuration reload, logical backend integration, and release automation.
Path validation, capability scope, root-link compatibility, and private listener propagation showed no additional confirmed defect.
The gateway preserves explicit and saved carrier choices.

The trial binary remained unchanged and had no restart or OOM kill during the initial read-only deployment checks.
The audit ran no disruptive tests against NAS or VPS.
Current health does not prove every recovery attempt succeeded or exclude future resource growth.
The trial lacks Prometheus history, as noted in the overnight review.
The browser scratch tests do not replace a complete Android or Windows end-to-end failure campaign.

Keep v0.6.8 as an unpublished draft.
Continue the Windows and Android trial with the corrected candidate before publication.
