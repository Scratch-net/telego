# v0.6.7 release audit

The audit covers all tracked changes after `v0.6.6`, plus the new regression tests and release notes.
The baseline commit is `a126e9343d382b23bce88d49dfe3d627d9d6de95`.

## Configuration and compatibility

- The gateway installer selects `websocket-lanes`. Its existing Nginx configuration forwards WebSocket upgrades.
- An explicit WEB carrier keeps its behavior. An absent or empty carrier still selects `https`.
- Configuration loading enables ME before TOML decoding. An explicit `enabled = false` overrides that default.
- Tests cover absent sections, empty sections, other ME parameters, and explicit enablement or disablement.
- INFO logs report ME establishment, unavailable ME connections, and explicit disablement.
- Direct fallback remains available during ME preparation and after preparation failures. Existing direct connections retain their route.
- The upgrade documentation identifies the default ME admission limit of 10,000 accepted clients, including direct fallback clients.
- The dashboard bundle omits one empty-value panel. Its metrics remain available.

## ME startup correction

Previously, the direct dialer opened TCP before it resolved a private source address through STUN.
The first sockets waited for cold discovery and the rest of the generation build before they sent a handshake.
VPS packet captures showed Telegram closing sockets before their first handshake bytes arrived.
The affected sockets waited approximately 6.7 seconds before their first payload.
Static public-IP controls avoided this initial failure.

The dialer now selects the local route address through a UDP socket without sending a datagram.
For a private route, it completes public-IP discovery before it opens TCP.
The TCP connection receives its full connection timeout after discovery.
The established socket still supplies the exact TCP source port and remote endpoint.
Public direct routes and SOCKS5 connections still bypass STUN.

The regression failed before the correction and passed afterward.
It covers private and public IPv4 and IPv6 routes, a static NAT address, discovery failures, cancellation, and the TCP timeout.
Separate checks cover a missing NAT resolver and the SOCKS5 bypass.

## Isolated VPS checks

The test binary used the production `poll_opt,gc_opt` build tags.
Each batch used a separate Docker image and private Docker network, with no published ports.
The configuration omitted both `middle-end.enabled` and `middle-end.nat-ip`.
Each run reached 48 ready links across 12 signed DC pools. ME admission remained available for another 10 seconds before cleanup.

| Batch | Cold starts | Starts without generation failures | Eventually ready |
|-------|-------------|------------------------------------|------------------|
| Initial correction | 3 | 2 | 3 |
| Follow-up with NAT capture | 3 | 2 | 3 |

Starts without failures reported ME establishment after approximately 10 seconds.
The INFO monitor samples every five seconds, so these times do not measure exact handshake completion.
Clean runs had approximately 0.5 seconds between TCP establishment and the first handshake payload.

The follow-up captured TCP SYN headers before and after Docker NAT.
Both failed handshake connections had different internal and external TCP source ports.
One port changed from `37148` to `48793`.
Another changed from `39276` to `17518`.
Both peers replied to the nonce and closed the stream after the encrypted handshake request.
The unchanged tuple derivation uses the internal TCP source port, which cannot authenticate those translated connections.
The existing retry path recovered, and all links became ready.

The first batch lacked an egress capture, so its external source ports remain unknown.
Its failed run also included idle closes during later repairs while the generation waited for other TCP connections.
The startup correction removes the STUN delay. It does not guarantee that every connection attempt succeeds.
Direct ME still requires NAT to preserve TCP source ports, as documented in the ME guide.

The production container ID, image, start time, and restart count remained unchanged across both batches.
All test containers, images, and networks were removed after the checks.

## Release checks

All release checks passed:

- `make test`: local gnet regressions, the full race suite, the `gc_opt` race suite, and the full production-tag suite.
- `make test-32 test-rpm`: 32-bit execution with production tags and RPM packaging checks.
- `golangci-lint run --timeout 5m`: zero issues.
- `goreleaser check -f dist/.goreleaser.yml`: valid release configuration.
- Static Linux builds with production tags for AMD64, ARM64, and ARMv7.
- Dashboard JSON parsing, panel counts, repeated merges, and panel overlap.
- `git diff --check`: no whitespace errors.

The release notes describe automatic ME startup, preserved explicit overrides, WEB carrier compatibility, and the NAT requirements.
The release workflow derives the binary version from the Git tag and reads `docs/releases/v0.6.7.md`.
