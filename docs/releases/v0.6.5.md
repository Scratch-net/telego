# v0.6.5 — Shared ME response memory and pressure diagnostics

Middle-End connections can recover from temporary client pauses without the former fixed response cutoff for each binding.
A shared memory budget bounds retained responses across clients and generation changes.

## Middle-End response buffering

- One service-wide pool covers queued responses and native or WEB frontend output across active and retiring generations.
- Bindings borrow available capacity instead of closing at the former 2 MiB or 768-event response limit.
- Output limits defer response processing. Partial writes retain their allocation charge until the buffer owner releases the allocation.
- The existing 100-second output stall timeout remains. Exhaustion of the shared pool can require an earlier closure.
- Pressure handling selects bindings with reclaimable backlog or retained output. Accepted responses remain ordered for connections that stay open.
- Replacement candidates reject unexpected application responses before copying packets into their event channel. Probes retain Ping/Pong support.

## Memory budget and monitoring

The default response pool is 69,231,118 bytes, approximately 66 MiB, on the current 64-bit build.
This includes response metadata, reserved output capacity, and the processing reserve.
Decoder storage, WEB carrier storage, request buffers, runtime memory, and kernel buffers have separate allowances.
The response pool is not a process RSS limit.

New metrics and diagnostics expose:

- Shared response usage, limits, and high-water marks, with memory classes and ownership stages.
- Admission waits, completed wait durations, and output stall closures.
- Response-pressure evictions, selection reasons, discarded queued bytes, and synchronously reclaimed budget charges.
- Registered ME links, including unpublished candidates.

Pressure diagnostics separate client eviction from physical-link failure.
The repository includes additional Grafana panels and a script to merge them into the existing dashboards.
Grafana updates remain a separate deployment step.

## Correctness fixes and regression coverage

- An aligned atomic connection counter fixes a connection-opening panic on 32-bit systems.
- Queue cleanup derives its event limit from allocation costs. On 32-bit systems, a maximum-size response can recover after backlog eviction before asynchronous cleanup runs.
- The gnet output path bounds write descriptors and clears retained references before allocation-release callbacks.
- Regression tests cover partial writes, ownership release, encrypted candidate responses, publication races, cancellation, and generation changes.
- Full test gates pass with race checks, production tags, and 32-bit execution. Both test and release workflows now require the 32-bit gate.
- Linux amd64, arm64, and ARMv7 production builds pass.

## Upgrade

Existing TOML configurations remain valid. This release adds no required configuration keys.
Request and frontend input budgets retain their existing derivation.

With an explicit nonzero `[middle-end].queue-budget-mb`, the combined response pool is twice that value and includes its processing reserve.
For example, `queue-budget-mb = 8` provides a 16 MiB response pool and separate 8 MiB request and frontend input budgets.
The default value of `0` adds the processing reserve to its ordinary response capacity.

Restart Telego after the upgrade. Keep the existing Nginx TLS configuration.
