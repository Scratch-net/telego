# v0.6.1 — Shared gnet core and Middle-End reliability

This release removes the default internal socket connection between WEB and MTProxy. It also adds proactive refresh of unused Middle-End links.

## Shared gnet core

- Native MTProxy and WEB streams use the same gnet session core, authentication, connection limits, and upstream routing.
- The private WEB HTTP/1.1 listener uses gnet. Nginx still terminates real TLS and serves ordinary HTTPS traffic.
- An explicit `[web-proxy].backend` retains the TCP or Unix socket compatibility path.
- Shutdown waits for connection cleanup and event-loop completion. A local gnet copy supplies the required lifecycle and owned-buffer fixes.

## Middle-End reliability

- Unused links become eligible for refresh after 45–60 seconds. A replacement must complete its handshake and return a matching RPC pong before admission.
- The current link stays available during preparation. A new client binding cancels the replacement, and existing bindings never move between physical links.
- Refresh work permits one candidate per signed DC and eight per manager, including cleanup. Failed candidates leave the current link unchanged.
- Late callbacks from an old link cannot close its replacement. A failed link still receives an independent repair without replacement of healthy DC pools.
- New metrics report refresh reservations, refresh outcomes, and losses of all ready links for a signed DC.
- Direct fallback stays available before ME admission. Each connection retains its selected route until it closes.

## Stream handling and diagnostics

- Buffer ownership and queue accounting cover partial writes, asynchronous callbacks, and connection closure.
- Queued output retains its byte order across direct, ME, and WEB paths. Shared WEB capacity wakes other eligible sessions after a release.
- Optional private diagnostics provide fresh Go 1.27 goroutine-leak checks, heap profiles, allocation profiles, goroutine profiles, and bounded CPU profiles.
- Diagnostics stay disabled by default. They require a literal loopback listener and must not pass through the public proxy.

## Deployment and packaging

- The managed gateway installer configures Telego, Nginx, certificates, automatic renewal, and persistent host storage.
- MTProxy and WEB can share port 443 or use separate public ports. The installer also supports MTProxy without WEB.
- The managed gateway makes its ACME webroot readable by Nginx workers. Certificate and configuration directories remain private.
- The openSUSE x86_64 RPM workflow supports parallel builds, preserves the active configuration on upgrades, and restricts access to secrets.
- The systemd installer uses the selected binary directory when `PREFIX` or `BINDIR` changes.
- Tests cover the local gnet module separately, including race builds and the production build tags.

## Upgrade

Existing configurations need no new required keys. ME, WEB, and diagnostics remain disabled unless the configuration enables them.

For the shared in-process WEB path, omit `[web-proxy].backend`. An existing explicit value continues to select a socket backend.

Keep Nginx as the real TLS endpoint. Restart Telego after the upgrade.

For an existing managed gateway, use the [gateway update procedure](https://github.com/Scratch-net/telego/blob/v0.6.1/examples/gateway/README.md#update-the-services).
It explicitly targets the existing directory and retains the selected layout and any pinned image.
It also corrects ACME webroot permissions without replacement of the existing configuration or secret.

Source builds require Go 1.27 or later and the complete repository, including `third_party/gnet`.
Use `make build` from a checkout. The local dependency replacement prevents installation with `go install …@version`.
